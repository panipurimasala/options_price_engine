Watch the solver converge

Enter a market price and the solver finds the σ that reproduces it, stopping when the model price is within $0.000001. Each row is one evaluation. When a Newton step would leave the bracket known to contain the answer, the solver bisects instead, which is what keeps it from failing on out-of-the-money options.

Volatility smile

Implied vol solved from real option chains

Each point is the engine's implied vol for one out-of-the-money contract: puts below spot, calls above. Constant-volatility Black-Scholes would draw a flat line. The curve is the smile, and it is exactly why the model does not "match market prices" with a single σ.

Does the engine give the right answer?

The test that matters is agreement with an independent implementation on identical inputs. For every contract, the engine's IV is fed to py_vollib, and the two prices are compared. Round-trip error alone would miss a bug shared by the pricer and solver.

Run it yourself

Fetch chains during US market hours, run the C++ engine over them, compare against py_vollib, then rebuild this page's data.

# build the engine and run the unit tests
cmake -S . -B build && cmake --build build
./build/parity_test

# validation pipeline (weekdays, 9:30–16:00 ET)
python vol_surface/fetch_validation_data.py
./build/market_validation validation_data.csv engine_output.csv
python vol_surface/compare_reference.py engine_output.csv

# refresh this page's data
python web/build_data.py validation_data.csv engine_output.csv --label "Live run, <date> <time> ET"

# re-verify the JavaScript port against the C++ build
c++ -std=c++20 -O2 -Iinclude web/verify_port.cpp build/libbs_core.a -o build/verify_port
./build/verify_port validation_data.csv > build/port_vectors.jsonl
node web/verify_port.mjs build/port_vectors.jsonl
